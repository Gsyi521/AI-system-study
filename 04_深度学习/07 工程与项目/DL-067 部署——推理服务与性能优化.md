# DL-067 部署：推理服务与性能优化

## 1. 本节学习目标

1. 会测**真实延迟**（warmup + 多次平均），并区分**延迟**与**吞吐**。
2. 用实测看"谁才是大头"：本课**批量化把每样本 12.6 μs 降到 0.19 μs（约 66 倍）**。
3. 理解为什么 JIT/量化/多线程在**小模型上反而更慢**（本课 0.0187 / 0.0982 / 0.0119 ms）。
4. 会写一个最小推理服务骨架（`no_grad` + `eval` + 批量）。

## 2. 为什么需要这个知识

因为"训练完"只是完成了一半：**上线后拼的是延迟、吞吐与稳定性**。

而且优化顺序错了会白干——本课的实测就说明：**先批量化**（66×），再谈 JIT/量化（这两个在本课甚至是负收益）。

## 3. 直观解释

| 指标 | 含义 | 优化手段 |
|---|---|---|
| **延迟**（latency） | 单个请求多久返回 | 减少算子、量化、缓存 |
| **吞吐**（throughput） | 每秒能处理多少 | **批量化**、并行、更大 batch |

**关键洞察**：**批量化几乎总是第一优先**——它把"每个样本的固定开销"摊薄。

## 4. 正式定义

**延迟与吞吐**

$$
\text{latency}=\frac{t_{\text{total}}}{N_{\text{req}}},\qquad
\text{throughput}=\frac{N_{\text{samples}}}{t_{\text{total}}}
$$

**本课两种口径**

| batch | 延迟 | 每样本 |
|---|---|---|
| 1 | 0.0126 ms | 12.6 μs |
| 256 | 0.0492 ms | **0.19 μs** |

## 5. 核心原理

**本课实测**

```text
单样本 eval+no_grad: 0.0143 ms
单样本 train 模式  : 0.0159 ms

batch=1  延迟: 0.0126 ms
batch=256 延迟: 0.0492 ms  每样本: 0.19 us

eager 0.0126 ms vs TorchScript 0.0187 ms
动态量化 INT8: 0.0982 ms（eager 0.0126 ms）

threads=1: 0.0113 ms
threads=2: 0.0119 ms
threads=4: 0.0119 ms

参数量: 513
```

**五个结论**：

1. **批量化是唯一显著的优化**：每样本 12.6 μs → **0.19 μs**（约 66 倍）。
2. `no_grad` 相对 train 模式只快一点（0.0143 vs 0.0159），因为模型太小；**大模型上差距会明显**。
3. **TorchScript 反而更慢**（0.0187 vs 0.0126）——小模型上编译/调度开销占主导。
4. **动态量化 INT8 更慢**（0.0982，约 8 倍）——量化在 CPU 小模型上常见负收益。
5. **多线程无收益**（1/2/4 线程 0.0113–0.0119）——计算量太小，线程调度开销抵消收益。

> **版本提示**：本机 PyTorch 2.15 里 `torch.jit.trace` 与 `torch.ao.quantization` 均已被标记为**弃用**（官方建议 `torch.compile` / `torchao`）。本课只记录实测数字，不对弃用 API 做推荐。

## 6. 数学表达式

**吞吐随 batch 的变化**

$$
\text{throughput}=\frac{B}{t(B)},\qquad t(B)=t_0+B\cdot t_1
$$

$t_0$ 是固定开销（调度/kernel 启动），$t_1$ 是每样本计算。

**每样本时间**

$$
\frac{t(B)}{B}=\frac{t_0}{B}+t_1
$$

本课：$B=1$ 时 12.6 μs（几乎全是 $t_0$）；$B=256$ 时 0.19 μs（已接近 $t_1$）。

## 7. 数学推导

**为什么小模型上 JIT/量化更慢**

设优化后每样本计算降为 $\alpha t_1$（$\alpha<1$），但引入额外固定开销 $c$：

$$
t_{\text{opt}}(B)=c+B\alpha t_1
$$

**加速比**：

$$
\frac{t(B)}{t_{\text{opt}}(B)}=\frac{t_0+Bt_1}{c+B\alpha t_1}
$$

- $B$ 很小时：$\frac{t_0}{c}$ —— 若 $c>t_0$，**加速比 < 1（变慢）**。
- $B$ 很大时：$\frac{1}{\alpha}$ —— 才体现优化收益。

本课 $B=1$、模型仅 513 参数 ⇒ 落在"变慢"区间（JIT 1.48×、量化 7.8× 更慢）。

## 9. 具体计算示例

```text
batch=1  : 0.0126 ms  → 每样本 12.6 μs
batch=256: 0.0492 ms  → 每样本 0.19 μs
提升倍数: 12.6 / 0.19 ≈ 66×
```

## 10. Python 实现

```python
import time

import torch
import torch.nn as nn


def latency_ms(fn, warmup: int = 10, iters: int = 50) -> float:
    for _ in range(warmup):
        fn()
    if torch.cuda.is_available():
        torch.cuda.synchronize()
    start = time.time()
    for _ in range(iters):
        fn()
    if torch.cuda.is_available():
        torch.cuda.synchronize()
    return (time.time() - start) / iters * 1000


model = nn.Sequential(nn.Linear(2, 128), nn.ReLU(), nn.Linear(128, 1))
model.eval()

x1 = torch.randn(1, 2)
x256 = torch.randn(256, 2)
with torch.no_grad():
    t1 = latency_ms(lambda: model(x1))
    t256 = latency_ms(lambda: model(x256))
print(f"batch=1  : {t1:.4f} ms  每样本 {t1 * 1000:.2f} us")
print(f"batch=256: {t256:.4f} ms  每样本 {t256 / 256 * 1000:.2f} us")
```

## 11. PyTorch 实现（最小推理服务骨架）

```python
import torch
import torch.nn as nn


class Predictor:
    def __init__(self, ckpt_path: str) -> None:
        self.model = nn.Sequential(
            nn.Linear(2, 32), nn.ReLU(), nn.Linear(32, 1)
        )
        state = torch.load(ckpt_path, map_location="cpu", weights_only=False)
        self.model.load_state_dict(state["model"])
        self.model.eval()

    @torch.no_grad()
    def predict_proba(self, x: torch.Tensor) -> torch.Tensor:
        return torch.sigmoid(self.model(x)).squeeze(-1)

    @torch.no_grad()
    def predict(self, x: torch.Tensor, threshold: float = 0.5) -> torch.Tensor:
        return (self.predict_proba(x) >= threshold).long()


# 造一个 checkpoint 供演示
import tempfile, os
path = os.path.join(tempfile.gettempdir(), "dl067_demo.pt")
net = nn.Sequential(nn.Linear(2, 32), nn.ReLU(), nn.Linear(32, 1))
torch.save({"model": net.state_dict()}, path)

predictor = Predictor(path)
x = torch.randn(5, 2)
print("概率:", [round(float(v), 4) for v in predictor.predict_proba(x)])
print("预测:", predictor.predict(x).tolist())
os.remove(path)
```

## 12. 代码逐行解释

| 代码 | 作用 |
|---|---|
| `warmup=10` | 排除首次调用的初始化开销 |
| `synchronize()` | GPU 异步，计时前必须同步 |
| `model.eval()` | 关闭 Dropout/BN 训练行为 |
| `@torch.no_grad()` | 推理不建图（省内存、更快） |
| `load_state_dict` | 只加载权重，需先建同结构 |
| `squeeze(-1)` | 把 `(N,1)` 压成 `(N,)` 便于阈值判断 |

**注意**：`threshold` 应在**验证集**上选，不能在测试集上调（DL-038 的教训）。

## 14. 应用场景

| 场景 | 优化重点 |
|---|---|
| 在线 API（低延迟） | 单样本快、模型小、量化可能有用 |
| 离线批处理 | **大批量**（本课 66×） |
| 边缘设备 | 量化/剪枝/小模型 |
| GPU 服务 | 动态批处理（Triton 等） |
| 高并发 | 多实例 + 队列 + 超时控制 |

## 15. 优点与缺点

| 手段 | 优点 | 缺点 |
|---|---|---|
| 批量化 | 收益最大（本课 66×） | 增加单次延迟 |
| `no_grad` + `eval` | 零成本、必做 | 收益随模型大小变化 |
| JIT/编译 | 大模型可提速 | 小模型更慢（本课 1.48×） |
| 量化 | 省内存、可加速 | 小模型更慢（本课 7.8×）、精度损失 |
| 多线程 | 大计算量有效 | 小计算量无收益 |

## 16. 常见错误

| 错误 | 现象 | 纠正 |
|---|---|---|
| 不 warmup 就计时 | 数字虚高 | 先跑 10 次 |
| GPU 不同步 | 延迟"几乎为 0" | `synchronize()` |
| 不做批量化就优化算子 | 收益 <2 倍 | 先批量 |
| 小模型上量化 | 更慢（0.0982） | 实测再定 |
| 推理忘 `eval()` | Dropout 引入随机性 | 切 eval |
| 在测试集调阈值 | 泄漏 | 用验证集 |

## 17. 本节总结

- **批量化是第一优先**：每样本 12.6 μs → **0.19 μs（约 66×）**。
- 小模型上 **JIT（0.0187）/量化（0.0982）/多线程** 都是**负收益**——优化必须实测。
- 推理服务三件套：`eval()` + `no_grad()` + 批量。

## 练习与参考答案

**基础 1**：延迟与吞吐有什么区别？本课各是多少？

**基础 2**：本课 batch=1 与 batch=256 的每样本耗时各是多少？提升多少倍？

**进阶 1**：为什么 TorchScript 与动态量化在小模型上反而更慢？

**综合**：你的在线推理服务 P99 延迟 800 ms，QPS 只有 5。请给出 4 个优化方向并说明优先级。

> [!success]- 参考答案

> **基础 1**
> - **延迟**：单个请求的响应时间（本课 batch=1 时 **0.0126 ms**）。
> - **吞吐**：单位时间处理的样本数（本课 batch=256 时每样本 **0.19 μs**，等效吞吐约 5.2M 样本/秒）。
> 二者常冲突：批量越大吞吐越高，但单请求延迟也变大。

> **基础 2**
> batch=1：**12.6 μs/样本**；batch=256：**0.19 μs/样本**；提升约 **66 倍**。

> **进阶 1**
> 因为优化引入**固定开销** $c$（编译调度、量化/反量化），而小模型本身计算量极小（本课仅 513 参数）。
> 此时 $t_{\text{opt}}=c+B\alpha t_1$ 中的 $c$ 主导 ⇒ 总时间反而上升（本课 JIT 1.48× 更慢、量化 7.8× 更慢）。
> 只有当 $B$ 足够大、$t_0+Bt_1$ 远大于 $c$ 时，优化才划算。

> **综合（参考）**
> **方向与优先级**：
> 1. **先定位瓶颈**（最高优先级）：用 profiler 看时间花在预处理/模型/后处理/网络；800 ms 对一个小模型明显异常。
> 2. **批量化 + 队列**：把并发请求聚合（本课 66× 收益）；注意会增大单请求延迟，需设最大等待时间。
> 3. **减少无谓开销**：`eval()`、`no_grad()`、避免每请求重建模型/加载权重、降低日志 I/O。
> 4. **模型侧**：减小输入尺寸/模型规模、量化或蒸馏（需实测收益）。
> **验证**：改完用同一压测脚本比 P50/P99 与 QPS；同时观察 CPU/GPU 利用率，确认瓶颈真的转移了。
